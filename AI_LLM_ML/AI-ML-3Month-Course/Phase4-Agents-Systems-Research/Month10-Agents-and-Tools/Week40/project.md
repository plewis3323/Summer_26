# Week 40 Project — Analysis-Copilot Prototype

## Objective

Build the month's deliverable: a prototype **analysis copilot** — one installed
command, `copilot "question"`, that takes a physics question in plain language
and drives your Week-39 MCP tools to a correct, quoted answer with no human in
the middle. The gate (from `03-Project-Roadmap.md`): the copilot **completes 3
scripted analysis tasks end-to-end unattended**. Alongside the prototype you
ship what makes it credible: a task-suite evaluation (`EVAL.md`), a reviewed
failure analysis (`failures.md`), and a short recorded demo. This is the
rehearsal for the Week 47 capstone track (a) — same architecture, toy-scale
data, full-scale discipline.

## Background — the workflow being wrapped

The copilot automates a real, daily piece of collider work: the **calibration
check**. (The course's resident context is sPHENIX, a detector at RHIC, the
Relativistic Heavy Ion Collider at Brookhaven National Lab — but the workflow
below is generic to any calorimeter experiment, and the toy data stands in for
any of them.)

The physics, self-contained: a **calorimeter** is the detector layer that
measures particle energies. Its response drifts with time and temperature, so
each **run** — a contiguous numbered data-taking period — gets a per-run
**calibration constant** (an energy-scale correction) determined offline and
marked good or bad. The standard probe of whether the calibration is right is
the **π⁰ meson**: it decays to two photons, and the **invariant mass**
reconstructed from photon pairs peaks at the known π⁰ mass, 0.135 GeV, on top
of smooth background. If the fitted peak sits at 0.135 GeV, the energy scale is
correct; if it is shifted, the calibration is off. So a physicist on shift
repeatedly answers the same few questions: *which runs exist? which have good
calibrations? where does the π⁰ peak sit in the latest run? is that consistent
with 0.135? set up the follow-up analysis job.* Those questions are exactly
what your five MCP tools answer — the copilot's job is to let you ask them in
one sentence instead of five commands.

## Build steps

Do them in order; each has its own accept line, and the exercises (E5, E6, E4)
supply three of them.

1. **Glue layer.** The async loop from lesson §4: launch the server, translate
   `list_tools()` into API tool definitions, dispatch `tool_use` blocks to
   `call_tool`, map protocol errors onto `is_error`, cap iterations, save the
   full transcript of every run to `transcripts/`. Accept when: a plain script
   answers "Fit the pi0 peak in the latest run" end-to-end through the server
   and the saved transcript shows the tool calls.
2. **The CLI.** Package `week40/copilot/` so `uv sync` installs a `copilot`
   entry point; `copilot "question"` prints the answer and writes the
   transcript. Keep it thin — argument in, glue function, answer out. Accept
   when: fresh clone + `uv sync` + one command answers 2 scripted demo
   questions end-to-end (exercise E5's criterion).
3. **The three scripted tasks.** `run_demo.py` runs these, in order, with no
   human input between launch and verdict, checking each programmatically:
   - **T1 — status check:** "Which is the latest run in `data/`, and is its
     calibration good or bad?" Check: names the highest-numbered run and its
     correct status from `calibrations.json`.
   - **T2 — calibration check:** "Fit the pi0 peak in the latest run with a
     good calibration and state whether the mass is consistent with 0.135 GeV
     within 2 sigma." Check: quoted mass within 2 MeV of the reference fit,
     and the stated verdict matches the reference computation.
   - **T3 — follow-up job:** "Generate a Fun4all macro skeleton for a pi0
     analysis of run 42, and report the fitted mass it should reproduce."
     Check: the macro passes the Week 39 E5 structure test and the quoted mass
     is within 2 MeV of the reference.
   Accept when: `run_demo.py` reports 3/3 passed, unattended, from a fresh
   clone.
4. **Evaluate.** Run the 10-task suite on the copilot; write `EVAL.md` with
   success rate (fraction, small-n caveat), mean cost per task, mean latency,
   and one prioritized improvement justified by a specific trajectory
   (exercise E6's criterion). Accept when: `EVAL.md` contains the numbers and
   the justified improvement.
5. **Failure analysis.** `failures.md`: 3 failing trajectories (from the suite,
   or harder probe tasks if the suite all passes), each annotated with its
   first wrong step and a root cause from the lesson §7 taxonomy (exercise
   E4's criterion). Accept when: each failure names a root cause and the fix
   it implies.
6. **Record the demo.** A short screen capture (2–4 minutes) of a real CLI
   session: the three scripted tasks plus one free-form question, narrated in
   a sentence or two. Accept when: the recording exists in the repo (or is
   linked from the README) and shows the fitted mass being quoted from a live
   run.

## Acceptance gate (end of Week 40 — from `03-Project-Roadmap.md` and the month README)

- The copilot **completes 3 scripted analysis tasks end-to-end unattended**
  (build step 3, from a fresh clone).
- Tested and reproducible: `pytest -q` green (the Week 39 server suite plus at
  least a smoke test on the glue), and fresh clone + `uv sync` + one command
  runs the demo.
- `EVAL.md` with success rate, cost per task, and latency; `failures.md` with
  ≥ 1 trajectory reviewed to a root cause; the recorded demo.
- Honesty over polish: an unflattering success rate with a correct diagnosis
  passes; a cherry-picked demo without numbers does not.

## Writeup requirements

A short `README.md` in `week40/copilot/` containing:

- **What it is and how to run it** — install, the one demo command, one example
  question with its answer.
- **Architecture** — a paragraph (diagram optional) naming the pieces and
  which week built each: MCP server (39), agentic loop (37), glue + CLI +
  evals (40), and why this design passed the Week 38 checklist.
- **Results** — the evaluation table (success rate, cost per task, latency)
  inlined or linked from `EVAL.md`, with the baseline comparison from E3 if
  you have it.
- **Limitations and what failed first** — written from `failures.md`, the day
  it happened, not reconstructed; include the first thing you would fix and
  why that one.
